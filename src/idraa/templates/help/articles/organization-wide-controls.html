What it does

Organization-wide is a flag on a control (the toggle on the control form). A flagged control's Variance Management (VMC) and Decision Support (DSC) functions apply to every scenario in the organization when an analysis runs, whether or not you link the control to that scenario. In run results the inherited copy is listed as “Patch Management (org-wide)” and carries an org-wide badge. A control is inherited only while it is published (status Active) and its implementation stage is Active; an unpublished control is never inherited.

Inherited functions have no standalone reduction. They act only by raising the reliability of the Loss-Event functions on the scenario's other controls (register entry C7), so a scenario that links no Loss-Event control gets nothing from them. Use the flag for a control that governs the organization's controls as a whole, instead of linking it scenario by scenario.

Eligibility

A control can be organization-wide only if it has at least one Variance Management or Decision Support function; Loss-Event-only controls cannot be. The toggle stays disabled until one of the control's function rows picks such a function.

Variance Management Identification and Implementation functions score as a pair across a scenario's active controls, inherited ones included: an Identification-only control contributes only where another control supplies Implementation, and the reverse. Decision Support's Identify-misalignment function pairs instead with a Correcting Misaligned Decisions link. Treatment Selection is label-only and score-neutral (register C8). The uplift raises the reliability of the Loss-Event functions on the scenario's other controls; it is not a standalone reduction.

Hybrid controls

A control can carry Loss-Event functions as well as Variance Management / Decision Support ones. Only the Variance Management / Decision Support functions are inherited. To credit the control's Loss-Event functions on a scenario, link the control to that scenario explicitly: the explicit link then applies the full control, and the inherited copy is not generated for that scenario.

A derived Correcting Misaligned Decisions row is inherited only when it is fulfilled by the control's own Variance Correction (Implementation) function. One fulfilled by a Loss-Event Response function (event termination or resilience) travels with that function and needs the explicit link (register entry C12). A control whose only Variance Management / Decision Support credit is such a Response-fulfilled link is therefore not eligible to be organization-wide.

The rule that a Correcting Misaligned Decisions link counts only when its source is a Variance Management function is about inheritance and eligibility. On a scenario that links the control explicitly, a link sourced from a Loss-Event Response function still completes the Decision Support pair (register entry C12).

Reading the numbers

An inherited row has no standalone reduction: considered on its own it changes no frequency, vulnerability or loss multiplier, so it reduces nothing by itself, which is also what the run page's inherited-controls note says. Its value shows up in the fair share and if-removed figures, which credit it for the reliability it adds to the scenario's other controls.

A control linked on one scenario and inherited on another appears as two rows, the plain name and the “(org-wide)” name. The rows are not merged and not double-counted, and the control's annual cost is counted once.

The “not double-counted” identity holds on the attribution's own calculation, not on the headline. Per scenario, the fair-share values add up to the modelled reduction the attribution uses, a closed-form figure computed from the controls' composed effect rather than a simulated one. On older runs, and for the muted “typical” figures beside the average on newer runs, that modelled reduction is a typical-case figure and will not match the headline mean ALE change. On the average basis of newer runs it is on the same basis as the headline but is still the closed-form reduction, not the simulated base-minus-residual difference, so do not expect the two to agree to the dollar.

Inherited rows count as controls toward the attribution limits, and every organization-wide control adds one to every scenario at once. Three limits apply, and the second and third are reached long before the first:

  • Per scenario. A scenario with more than 64 controls, inherited ones included, gets no fair-share figures. Its if-removed figures are still computed.
  • Per run. Fair shares cost 2n calculations for a scenario with n controls up to 12, and about 4,600 per control above that, against a budget of 2,000,000 calculations for the whole run. Scenarios are taken in stored order. A scenario whose cost no longer fits what is left of the budget gets no fair shares, which are then unavailable for it and show — in the matrix, and a later, smaller scenario may still fit. At 12 controls per scenario about 490 scenarios fit; at 13, about 33. If every scenario is skipped, the run page says per-control attribution isn’t available for the run.
  • Ranking stability. The weight-uncertainty check runs up to 256 draws under its own budget of 10,000,000 calculations. A larger run can afford fewer draws. Below 32 the check is not run: only three band-endpoint draws are evaluated, and the run page says “Ranking-stability check skipped — too few simulation draws”. Ten scenarios of 13 controls could afford 34 draws, so the check ran; ten of 20 controls could afford 21, and 400 scenarios of 12 controls could afford 11, so it was skipped.

Authoring reliability

A control's authored reliability is its expected reliability absent meta uplift (register entry C7). With organization-wide controls that convention now applies by default to every scenario. An estimate taken from observed, in-situ performance already includes that environment, so the uplift counts it twice and the modelled reliability will read high.

The meta assignment's coverage is the lever for how much of the organization's Loss-Event controls the control actually governs: lowering it lowers the uplift every scenario receives. The register (entry C7a) records the inheritance as an applicability default and bounds its effect: a wrongly inherited control moves any Loss-Event assignment's effective reliability by at most 0.1 absolute at the library's reliability of 0.8.

Re-runs

Only a change to an organization-wide control that is in effect (flagged organization-wide, published, implementation stage Active) marks analyses as needing a re-run. When such a control is flagged or unflagged, published, deprecated, demoted from Active, deleted, re-synced from the library or has its functions edited (including adding or clearing its Correcting Misaligned Decisions link), every completed analysis in the organization is marked, because every scenario's composition changed, not just the scenarios that linked the control. The same edits to a control that is not in effect (a Draft or Planned one, or one that is not flagged) change no scenario and mark nothing. A run created before organization-wide controls existed says so on its page when the organization now has any in effect, and shows what a re-run would add.

Clearing the flag is always an explicit act: the toggle stays enabled while it is on, and a save that would leave an organization-wide control without any Variance Management / Decision Support function is refused rather than silently un-flagging it.
